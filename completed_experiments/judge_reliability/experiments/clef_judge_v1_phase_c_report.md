# Clef judge experiment: Phase C report

Experiment: `clef_judge_v1.md` (PR #126). Follows the Phase A preflight and Phase B standardized comparison. Run date: 2026-10-06.

Phase C has two panels. **The near-context stress panel was run. The real-transcript agreement panel could not be run**, because its inputs are not in the repository (details below).

## Near-context stress panel

Full Clef was 9/9 correct: 3/3 at baseline and 3/3 in each long-context condition, with inputs of about 15,200 tokens (93% of the 16,384-token limit).

| Condition | Correct | Input tokens | Latency per call |
|---|---:|---:|---:|
| Baseline (no filler) | 3/3 | 484 to 519 | 0.49 to 1.0 s |
| Ground truth early (filler before it) | 3/3 | 15,221 to 15,256 | 7.9 s |
| Ground truth late (filler after it) | 3/3 | 15,222 to 15,257 | 8.0 s |

| Case | Expected | Clef p(correct): baseline | early | late |
|---|---|---:|---:|---:|
| judge-001 | hold | 0.953 | 0.938 | 0.948 |
| judge-003 | diverge | 0.965 | 0.965 | 0.963 |
| judge-005 | abstain | 0.941 | 0.933 | 0.944 |

Adding about 62,000 characters of unrelated text moved the correct label's probability by at most 0.015, and the position of the ground truth (before or after the filler) made no difference to any label.

Results for the #122 candidates on their version of this panel, for context only: Qwen3 4B Instruct 2507 9/9, Llama 3.2 3B 8/9, Gemma 3 4B 5/9. See the caveats before comparing.

### Truncation guard probe

The guard added earlier (`check_no_truncation`, commit `10bf048`) had only been tested with a stub encoder. The runner now also feeds the guard an input with 124,000 characters of filler, using Clef's real encoder. It raised, as intended, and no model call was made:

> Input is 30203 tokens, over max_length=16384; Clef would silently truncate 13819 trailing state tokens from candidate_response.

So an input past the limit is reported as a failure rather than being judged on a clipped candidate response.

### Caveats

1. **This is a reconstruction, not #122's exact panel.** #122 publishes the panel's design and results but not its filler text or the script that built it. The runner (`run_clef_context_stress.py`) follows the published design: cases judge-001, 003 and 005; 62,000 characters of neutral filler; placed before or after the ground truth inside the ground-truth field; candidate answer and expected label fixed. The filler itself is generated by this script (hash `810159c3…`). Treat the comparison with Qwen, Llama and Gemma as directional only.
2. **Different tokenizer and input format.** Clef's input is a typed JSON request tokenized by Clef's tokenizer, so about 15,200 tokens here is not the same quantity as the roughly 14,500 tokens #122 reported from Ollama for the same character count.
3. **Small and easy.** Three cases, a filler that is obviously unrelated, and one run each. It shows the model still reads the relevant text at 93% of its limit with a clean distractor. It does not show robustness to relevant but misleading long context, or to inputs near the limit built from real conversations.
4. **Latency scales with input.** Median latency went from about 0.5 s at roughly 500 tokens to about 7.9 s at roughly 15,200 tokens. Part of this is the torch fallback for attention layers (the fast path libraries were not installed), so it may overstate Clef's cost.

## Real-transcript agreement panel: not run

This is the first criterion in the proposal's decision rule, so **no judge recommendation can be made until it is run.**

#122 reports a 20-response panel built from six real solver conversations (Qwen3 4B Instruct as the solver), with one human reviewer's labels (18 hold, 2 diverge, 0 abstain). The repository contains only the *predictions* for the three local judges (`transcript_agreement/*_predictions.jsonl`: response ids, the human label, the model's label and token counts). It does not contain what was judged: the six conversations, the response-level grading units with their preceding-turn context, the reference-label file, or the script that produced the predictions. I searched #122's branch, `main`, the Hub org's other repositories (there are none besides this Space) and this machine; none holds them. I did not open every other PR's file list, so they may exist somewhere I did not look.

Without the inputs, running Clef would require inventing the transcripts, which would make the result meaningless as agreement with the human labels.

**What is needed (from the #122 author):** the panel input file (six conversations split into the 20 response-level units, with the turn context each judge received on later turns and the opening-turn `transcript=None` handling noted in #122's report) plus the human reference labels and the script that built the judge input. With those, the Clef run is a short job on the same hardware, and the adapter needs one extension: mapping a response plus its preceding turns into Clef's state.
